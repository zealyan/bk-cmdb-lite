# 权限配置使用手册（面向 DB / SQL 操作）

> 适用范围：`cmdb_server_lite`（Flask + SQLite，内置轻量 RBAC，无外部 IAM）。
> 本文聚焦**如何通过直接操作数据库（SQL）来配置用户与权限**，并以
> 「`tom` 用户，对模型 `bk_slb_listener` **可新增、不可编辑、不可删除**」为完整示例。
>
> 设计原理详见同目录 `权限设计方案.md`；本文是「怎么配」的操作手册。

---

## 一、鉴权总览（先理解再动手）

整个鉴权是 **「双层门禁 + 一个总开关」**：

| 维度 | 说明 |
|------|------|
| 总开关 `ENABLE_AUTH` | `false`（默认）时**全局短路放行**，所有请求视为超管，权限配置不生效。只有 `true` 时才真正鉴权。 |
| 登录开关 `SKIP_LOGIN` | `true`（默认）时回落为默认超管用户，不强制登录。要真正按用户区分权限，必须设为 `false` 并走 `POST /api/v1/auth/login` 拿 token。 |
| 网关层（粗粒度/模型级） | `app/auth/manager.coarse_authorize` + `authorizer.BuiltinAuthorizer`：按「模型 + 动作」判定。 |
| 实例层（细粒度/owner） | `app/auth/manager.check_instances`：按实例 `creator` / `bk_supplier_account` 逐实例判定。 |

**单条请求的判定顺序（任一命中即放行）**：
1. 读操作（`find`）：**永远放行**（SkipReadAuthorization）。
2. 管理员（`bk_role == 1`）：**全权放行**。
3. 创建者自管：实例 `creator == 当前用户` → 放行（仅对该实例的 edit/delete/find）。
4. 模型级策略：`cc_AuthPolicy` 命中 `allow` → 放行（对该模型**全部**实例的该动作）。

> ⚠️ **创建（create）现已纳入门禁（行为变更）**：以往实例创建对全体「已登录非管理员」用户开放；
> 现已对齐上游——`create` 是独立注册的动作（`genDynamicAction` 的 `Create_<模型>`），创建前
> **必须单独授予 `create` 策略**，否则返回 `1302102`。
> 这与「创建者自管」是两件独立的事：创建者自管是「创建**后**」凭实例 `creator` 列获得自身实例的
> `edit/delete/find`；而 `create` 动作本身在创建**前**就须过门禁（上游 `RegisterResourceCreatorAction`
> 只授 `edit/delete/find`，**不含 create**）。即「不可新增」现在可用「不授 create 策略」实现。

> ⚠️ 本系统是 **「默认拒绝、策略允许」** 模型：`cc_AuthPolicy` 只有 `effect='allow'` 这一种取值，
> **没有 deny 行**。所以「不可编辑 / 不可删除」= **不插入对应的 allow 行**（留白即拒绝）。

## 二、两张核心表

所有用户与权限都落在这两张表里（库文件：`cmdb_server_lite/cmdb_dev.db`）。

### 2.1 用户表 `cc_UserBase`

| 列 | 类型 | 说明 |
|----|------|------|
| `bk_user_id` | INTEGER PK | 自增主键 |
| `bk_user_name` | TEXT **UNIQUE** | 登录用户名（也是策略里的 `principal`） |
| `bk_supplier_account` | TEXT DEFAULT '0' | 供应商账户（多租户隔离维度，默认 `'0'`） |
| `bk_role` | INTEGER DEFAULT 2 | `1`=超级管理员（全权），`2`=普通用户（受策略约束） |
| `bk_password` | TEXT | **werkzeug 哈希**，绝不存明文 |
| `create_time` | TEXT | 创建时间 |

> 身份解析四路来源（优先级）：`Authorization: Bearer <token>` → `bk_token` cookie →
> `bk_username` / `X-User` 请求头 → 配置默认用户 `admin`。**策略匹配的是 `bk_user_name` 字符串**。

### 2.2 权限表 `cc_AuthPolicy`

| 列 | 类型 | 说明 |
|----|------|------|
| `id` | INTEGER PK | 自增主键 |
| `supplier` | TEXT NOT NULL | 供应商账户（必须与用户 `bk_supplier_account` 一致才命中） |
| `principal` | TEXT NOT NULL | 用户名（= `cc_UserBase.bk_user_name`） |
| `res_type` | TEXT NOT NULL | 资源类型，取值见下表（受网关拦截 = 该类型会被 `app/auth/parser.py` 产出并判定；reserved = 当前路由未暴露、写库无害但不生效） |
| `obj_id` | TEXT | **模型级**作用域 = 模型 ID（如 `bk_slb_listener`）；`NULL` = 该类全部模型 |
| `action` | TEXT NOT NULL | 动作：`create` / `update` / `delete` / `find` |
| `effect` | TEXT DEFAULT 'allow' | 仅 `'allow'`（无 deny） |
| `business_id` | VARCHAR(64) | 业务级作用域（`biz_topology` / `hostInstance` 专用）；`NULL` = 全部业务（类级，业务无关）；指定值（如 `'2'`）= 仅该业务的集群/模块/转移生效。对齐上游 `bizTopology` 的 `Parents=[business]` |

> **`obj_id` 是模型 ID，不是实例 ID。** 它必须等于接口路由里的 `<model_id>`：
> `POST /api/v1/models/<model_id>/instances` → `obj_id = <model_id>`。
> 实例 ID（`bk_inst_id`）只用于「创建者自管」判定，**不参与策略匹配**。

### 2.3 资源类型（`res_type`）速查

| `res_type` | 受网关拦截 | 可用动作 | `obj_id` 取值 | 说明 |
|---|---|---|---|---|
| `modelInstance` | ✅ | `create` / `update` / `delete` / `find` | 模型 ID（省略=全部模型 `NULL`） | 业务拓扑之外的模型 CRUD |
| `biz_topology` | ✅ | `create` / `update` / `delete` | 固定 `biz_topology`（或 `NULL` 类级）；业务级再经 `business_id` 隔离（`NULL`=全部业务，指定值=仅该业务） | 集群 / 模块 / 主线实例，上游 IAM 统一映射 |
| `hostInstance` | ✅ | `transfer` | 固定 `host`（或 `NULL` 类级）；业务级同样可经 `business_id` 隔离 | 主机转移（与主机 `update` 解耦） |
| `business` | ❌ reserved | — | — | 当前路由未暴露业务级写，网关暂不拦截 |
| `model` | ❌ reserved | — | — | 模型元数据管理，解析器未产出该类型 |

> 集群/模块/主线实例在**上游 IAM 侧统一为一个资源类型 `biz_topology`**（lite 与上游对齐），
> 因此「创建集群 / 创建模块 / 编辑 / 删除」都归到 `biz_topology` 的 `create/update/delete`。
> 主机转移在上游是专用动作，lite 用独立的 `transfer` 动作区分于主机自身的 `update`。
> 设计细节见 `权限设计方案.md` §十。

## 三、先把鉴权打开

权限配置只有在「鉴权开启且强制登录」时才生效。修改后端启动环境变量：

```bash
# cmdb_server_lite 启动环境
export CMDB_ENABLE_AUTH=true     # 开启鉴权（默认 false）
export CMDB_SKIP_LOGIN=false     # 关闭免登录，强制走 token（默认 true）
```

重启后端后：
- 未带 token 的请求 → 返回 `bk_error_code=1302100`（未登录）。
- 普通用户（非 admin）的写操作 → 按 `cc_AuthPolicy` 判定，无策略即 `1302102`（无操作权限）。

> 本手册的 SQL 无论鉴权是否开启都能执行（直接改库）；但**只有开启后才会真正限制请求**。

## 四、SQL 操作速查

> 环境无 `sqlite3` CLI，下方给出两种执行方式：
> - **方式 A（推荐，最贴近"面向 DB 的 SQL"）**：用 Python 直接操作 `cmdb_dev.db`。
> - **方式 B（走应用层）**：在 Python 里调用 `app.db.executor` 的 `insert/execute/query_one`。
>
> 密码必须是 werkzeug 哈希，不能直接写明文。

### 4.1 新增用户

```sql
INSERT INTO cc_UserBase (bk_user_name, bk_supplier_account, bk_role, bk_password, create_time)
VALUES (:u, :s, :r, :hashed_pwd, :t);
```

参数：
- `:u` 用户名；`:s` 供应商账户（与策略 `supplier` 对应）；`:r` 角色 `1` 或 `2`；
- `:hashed_pwd` = `werkzeug.security.generate_password_hash(明文密码)`；
- `:t` 当前时间串，如 `'2026-08-12 00:00:00'`。

### 4.2 为用户授权（写 `cc_AuthPolicy`）

```sql
INSERT INTO cc_AuthPolicy (supplier, principal, res_type, obj_id, action, business_id, effect)
VALUES (:s, :p, 'modelInstance', :o, :a, NULL, 'allow');
```

- `:s` 供应商账户（须 == 用户的 `bk_supplier_account`）。
- `:p` 用户名（== `cc_UserBase.bk_user_name`）。
- `:o` 模型 ID（== 接口路由里的 `<model_id>`）；传 `NULL` 表示「该类全部模型」。
  拓扑/转移场景 `:o` 取固定字面量（与 §2.3 一致）。
- `:a` 动作：`create` / `update` / `delete` / `find` / `transfer`。
- `:biz` 业务级作用域：`obj_id` 之外可再传 `business_id`；`NULL`（或不写）= 全部业务（类级），指定值（如 `'2'`）= 仅该业务。拓扑/转移场景可用。

**业务拓扑 / 主机转移授权示例**（与 §2.3、解析器产出的 `obj_id` / `business_id` 严格对齐）：

```sql
-- 授予「拓扑管理员」：集群/模块 可增改删（business_id=NULL 类级，单条覆盖全部业务）
INSERT INTO cc_AuthPolicy (supplier, principal, res_type, obj_id, action, business_id, effect)
VALUES (:s, :p, 'biz_topology', 'biz_topology', 'create', NULL, 'allow'),
       (:s, :p, 'biz_topology', 'biz_topology', 'update', NULL, 'allow'),
       (:s, :p, 'biz_topology', 'biz_topology', 'delete', NULL, 'allow');

-- 等价写法：obj_id 留 NULL（类级），因网关判定 (obj_id = ? OR obj_id IS NULL) 同样命中
INSERT INTO cc_AuthPolicy (supplier, principal, res_type, obj_id, action, business_id, effect)
VALUES (:s, :p, 'biz_topology', NULL, 'create', NULL, 'allow'),
       (:s, :p, 'biz_topology', NULL, 'update', NULL, 'allow'),
       (:s, :p, 'biz_topology', NULL, 'delete', NULL, 'allow');

-- 仅授予「业务 2」的拓扑管理员（business_id='2' 业务级策略，仅对业务 2 生效，与类级互不覆盖）
INSERT INTO cc_AuthPolicy (supplier, principal, res_type, obj_id, action, business_id, effect)
VALUES (:s, :p, 'biz_topology', 'biz_topology', 'create', '2', 'allow'),
       (:s, :p, 'biz_topology', 'biz_topology', 'update', '2', 'allow'),
       (:s, :p, 'biz_topology', 'biz_topology', 'delete', '2', 'allow');

-- 授予「主机转移」权限（transfer，与主机 update 解耦；business_id 同样可指定业务）
INSERT INTO cc_AuthPolicy (supplier, principal, res_type, obj_id, action, business_id, effect)
VALUES (:s, :p, 'hostInstance', 'host', 'transfer', NULL, 'allow');
```

### 4.3 查询 / 校验

```sql
-- 查某用户在某模型上的全部授权
SELECT action, effect, obj_id
FROM cc_AuthPolicy
WHERE supplier = :s AND principal = :p AND (obj_id = :o OR obj_id IS NULL);

-- 查所有用户
SELECT bk_user_name, bk_supplier_account, bk_role FROM cc_UserBase;

-- 内置判定等价于（可用来自检某动作是否会被放行）：
SELECT effect FROM cc_AuthPolicy
WHERE supplier = :s AND principal = :p
  AND res_type = 'modelInstance'
  AND (obj_id = :o OR obj_id IS NULL)
  AND (business_id = :b OR business_id IS NULL)
  AND action = :a
LIMIT 1;   -- 命中且 effect='allow' → 允许；否则默认拒绝（find 除外，读永远放行）
            -- 拓扑/转移场景把 res_type 换成 biz_topology/hostInstance，business_id 设为请求业务或 NULL（类级）
```

### 4.4 撤销 / 回收权限

```sql
-- 按主键删
DELETE FROM cc_AuthPolicy WHERE id = :id;

-- 按「用户 + 模型 + 动作」精确删
DELETE FROM cc_AuthPolicy
WHERE supplier = :s AND principal = :p AND obj_id = :o AND action = :a;
```

### 4.5 修改用户 / 锁定账号

```sql
-- 改角色（如提权为管理员）
UPDATE cc_UserBase SET bk_role = 1 WHERE bk_user_name = 'tom';

-- 重置密码（必须先哈希）
UPDATE cc_UserBase SET bk_password = :hashed_pwd WHERE bk_user_name = 'tom';

-- 锁定：把角色改成不存在的值或删除账号（删除需先清理其策略行）
DELETE FROM cc_AuthPolicy WHERE principal = 'tom';
DELETE FROM cc_UserBase  WHERE bk_user_name = 'tom';
```

### 4.6 批量授权（一类模型全部可写）

```sql
-- obj_id = NULL 表示对该 supplier 下「全部模型」授予某动作
INSERT INTO cc_AuthPolicy (supplier, principal, res_type, obj_id, action, effect)
VALUES (:s, :p, 'modelInstance', NULL, 'create', 'allow');
```

## 五、实战示例：tom 对 `bk_slb_listener` 可新增、不可编辑、不可删除

### 5.1 需求拆解

| 目标 | 实现方式 |
|------|----------|
| **可新增（create）** | 插入一行 `action='create'` 的 allow 策略 |
| **不可编辑（update）** | **不插入** `action='update'` 的 allow 行 → 默认拒绝 |
| **不可删除（delete）** | **不插入** `action='delete'` 的 allow 行 → 默认拒绝 |

> 关键认知：**「不可编辑 / 不可删除」不是写一条 deny，而是「什么都不写」**。
> 本系统的拒绝来自「策略表里没有 allow」，留白即拒绝。

### 5.2 完整 SQL（可直接执行）

> 下面脚本用 Python 直连 `cmdb_dev.db`。**密码必须先哈希**，脚本已内置。
> 执行前请确认后端已按第三章开启 `ENABLE_AUTH=true` + `SKIP_LOGIN=false`。

```python
# apply_tom_slb.py  —— 在 cmdb_server_lite/ 目录下运行
import sqlite3
from werkzeug.security import generate_password_hash

DB = "cmdb_dev.db"
SUPPLIER = "0"          # tom 的供应商账户，须与策略 supplier 一致
USER, PASS = "tom", "Tom@123456"
MODEL = "bk_slb_listener"

c = sqlite3.connect(DB)
cur = c.cursor()

# 1) 创建用户 tom（普通用户 bk_role=2）
cur.execute(
    """INSERT OR IGNORE INTO cc_UserBase
       (bk_user_name, bk_supplier_account, bk_role, bk_password, create_time)
       VALUES (?, ?, 2, ?, datetime('now'))""",
    (USER, SUPPLIER, generate_password_hash(PASS)),
)

# 2) 授权 create（可新增）
cur.execute(
    """INSERT INTO cc_AuthPolicy (supplier, principal, res_type, obj_id, action, effect)
       VALUES (?, ?, 'modelInstance', ?, 'create', 'allow')""",
    (SUPPLIER, USER, MODEL),
)
# 注意：update / delete 故意不插入 → 默认拒绝（不可编辑、不可删除）

c.commit()

# 校验
cur.execute("SELECT bk_user_name,bk_role FROM cc_UserBase WHERE bk_user_name=?", (USER,))
print("用户:", cur.fetchone())
cur.execute("SELECT action,effect FROM cc_AuthPolicy WHERE principal=? AND obj_id=?", (USER, MODEL))
print("权限:", cur.fetchall())
c.close()
```

执行后，`cc_UserBase` 多出 `tom`（角色 2），`cc_AuthPolicy` 仅有一行：
`(supplier='0', principal='tom', res_type='modelInstance', obj_id='bk_slb_listener', action='create', effect='allow')`。

### 5.3 配置后的行为预期

| 操作 | 接口 | tom 结果 | 原因 |
|------|------|----------|------|
| 查看列表 | `GET /api/v1/models/bk_slb_listener/instances` | ✅ 放行 | `find` 读操作永远放行 |
| **新增** | `POST /api/v1/models/bk_slb_listener/instances` | ✅ 放行 | 策略命中 `create=allow` |
| **编辑他人实例** | `PUT /api/v1/models/bk_slb_listener/instances/<他人id>` | ❌ `1302102` | 无 `update` allow，且非创建者 |
| **删除他人实例** | `DELETE /api/v1/models/bk_slb_listener/instances/<他人id>` | ❌ `1302102` | 无 `delete` allow，且非创建者 |
| 编辑/删除**自己创建**的实例 | `PUT/DELETE .../<自己id>` | ✅ 放行 | **创建者自管**规则优先于策略 |

### 5.4 ⚠️ 必须知道的边界（避免误配）

1. **「不可编辑/删除」仅针对他人创建的实例。**
   tom 自己 `POST` 创建的实例，`creator=tom`，依「创建者自管」规则 tom 仍可读/改/删**它自己那条**。
   这是与上游一致的所有权语义——无法用模型级策略剥夺创建者对自己实例的权限。
   若需求是「tom 连自己的也不能改/删」，那与本系统「创建即自管」模型冲突，只能**不给 create**（但那样又无法满足"可新增"）。

2. **读（`find`）永远放行**，与是否授权无关。不要试图用策略去"禁止查看"。

3. **`obj_id` 必须精确等于模型 ID。** 路由是 `/api/v1/models/<model_id>/instances`，
   策略里的 `obj_id` 要填同一个 `<model_id>`（区分大小写）。填错模型 ID 会导致策略永不命中。

4. **`supplier` 必须匹配。** 策略 `supplier` 与用户 `bk_supplier_account` 必须一致（默认都是 `'0'`），否则跨租户不可见。

5. **没有 deny，只有 allow。** 想"收回"某权限，用 `DELETE`（见 4.4），而不是写 `effect='deny'`（`deny` 不被识别，会被当作无效数据）。

6. **`bk_role=1` 的用户（admin）不受任何策略约束**，全权放行。不要把需要被限制的用户设为 1。

### 5.5 用 CLI 授权（推荐，等价于 SQL）

上面的 SQL 都有等价的 CLI 命令（`cmdb auth ...`，见 `CLI使用手册-权限设置篇.md`）。CLI 复用同一套
`app/db/auth.py` 公共数据层（多方言 + 项目 db 框架），与后端 API 共用同一套 SQL/方言逻辑，是 RBAC 的「单一真相源」。
**额外能力**：`--res-type` 指定资源类型、`grant-scenario` 按场景批量授权，省去手写多行 INSERT。

先确认可取的值（避免拼错）：

```bash
python3.11 -m app.cli.cmdb auth res-type list   # 列出 5 种 res_type + 说明 + 可用动作
python3.11 -m app.cli.cmdb auth action list     # 列出合法动作：create,update,delete,find,transfer
```

### 5.6 实战：授予 tom「拓扑管理员」+「可转移主机」

| 目标 | 实现方式（CLI） |
|------|----------------|
| **拓扑管理员（全部业务）** | `auth policy grant --res-type biz_topology --action create,update,delete`（省略 `--biz-id` = 类级，覆盖全部业务） |
| **拓扑管理员（仅业务 2）** | `auth policy grant --res-type biz_topology --action create,update,delete --biz-id 2`（仅对业务 2 生效，与类级独立） |
| **可转移主机** | `auth policy grant --res-type hostInstance --action transfer`（可加 `--biz-id` 限定业务） |
| **（等价批量）** | `auth policy grant-scenario --scenario topo-admin [--biz-id 2]` + `--scenario host-transfer` |

```bash
# 在 cmdb_server_lite/ 下执行；建议先停后端或用 --db 副本（见 CLI使用手册 §7.1）避免 SQLite 锁
python3.11 -m app.cli.cmdb auth policy grant --user tom --res-type biz_topology \
    --action create,update,delete
# 预期：退出 0，“已为 tom 在 全部模型(NULL)（biz=ALL）授权 ['create', 'update', 'delete']：新增 3 / 跳过 0”

# 仅对业务 2 授予拓扑管理员（business_id='2'，与上面的类级策略是两条独立行）
python3.11 -m app.cli.cmdb auth policy grant --user tom --res-type biz_topology \
    --action create,update,delete --biz-id 2
# 预期：退出 0，“已为 tom 在 全部模型(NULL)（biz=2）授权 ['create', 'update', 'delete']：新增 3 / 跳过 0”

python3.11 -m app.cli.cmdb auth policy grant --user tom --res-type hostInstance --action transfer
# 预期：退出 0，“已为 tom 在 全部模型(NULL)（biz=ALL）授权 ['transfer']：新增 1 / 跳过 0”

# 仅对业务 2 授予主机转移权（business_id='2'，仅业务 2 的模块可转移主机；与上面类级策略独立）
python3.11 -m app.cli.cmdb auth policy grant --user tom --res-type hostInstance --action transfer --biz-id 2
# 预期：退出 0，“已为 tom 在 全部模型(NULL)（biz=2）授权 ['transfer']：新增 1 / 跳过 0”
#   效果：tom 把主机转移到业务 2 模块放行；转移到业务 1 模块被拒 1302102
#   （请求时业务作用域由目标 module_id 反查 cc_ModuleBase.bk_biz_id 得到）

# 校验（list 也支持 --biz-id 过滤；biz 列显示 2 / ALL）
python3.11 -m app.cli.cmdb auth policy list --user tom --res-type biz_topology
python3.11 -m app.cli.cmdb auth policy list --user tom --res-type hostInstance
```

> 说明：`--res-type biz_topology` 省略 `--model` 时 `obj_id=NULL`（类级）；**省略 `--biz-id` 时 `business_id=NULL`（类级，覆盖全部业务）**。因网关判定
> `obj_id = ? OR obj_id IS NULL` 与 `business_id = ? OR business_id IS NULL`，类级策略对**全部业务**的拓扑写均命中（业务无关）——旧的「业务无关」行为默认保留。
> 也可显式写 `--model biz_topology`（精确匹配，效果相同）。**加 `--biz-id 2`** 则写入 `business_id='2'` 的独立业务级策略，仅对业务 2 放行、对业务 1 仍拒（与类级互不覆盖、互不幂等）。主机转移 `obj_id` 固定为 `host`，同样支持 `--biz-id`。

**配置后行为预期**（开启 `ENABLE_AUTH=true` + `SKIP_LOGIN=false`，以 tom 身份请求）：

| 操作 | 接口 | tom 结果 | 原因 |
|------|------|----------|------|
| 查看拓扑树 | `GET /api/v1/topo/biz` 等 | ✅ 放行 | `find` 读永远放行 |
| 创建集群 | `POST /api/v1/topo/biz/<bizId>/set` | ✅ 放行 | `biz_topology: create` 命中 |
| 编辑集群/模块 | `PUT /api/v1/topo/node/<objId>/<instId>` | ✅ 放行 | `biz_topology: update` 命中 |
| 删除模块 | `DELETE /api/v1/topo/node/module/<id>` | ✅ 放行 | `biz_topology: delete` 命中 |
| 主机转移 | `POST /api/v1/host/transfer/modules` | ✅ 放行 | `hostInstance: transfer` 命中 |
| 模型实例创建（未授权） | `POST /api/v1/models/<m>/instances` | ❌ `1302102` | 仅授了拓扑/转移，未授模型 `create` |

## 七、常见动作取值速查

| 动作常量 | 含义 | 资源类型 | 对应接口 |
|----------|------|----------|----------|
| `create` | 新增实例 | `modelInstance` | `POST /api/v1/models/<m>/instances` |
| `update` | 编辑实例 | `modelInstance` | `PUT /api/v1/models/<m>/instances[/<id>]` |
| `delete` | 删除实例 | `modelInstance` | `DELETE /api/v1/models/<m>/instances[/<id>]` |
| `find` | 查看实例 | `modelInstance` | `GET /api/v1/models/<m>/instances*`（**永远放行**） |
| `create` | 创建集群 / 模块 | `biz_topology` | `POST /api/v1/topo/biz/<bizId>/set`、`POST /api/v1/topo/set/<setId>/module` |
| `update` | 编辑集群 / 模块 | `biz_topology` | `PUT /api/v1/topo/node/<objId>/<instId>` |
| `delete` | 删除集群 / 模块 | `biz_topology` | `DELETE /api/v1/topo/node/<objId>/<instId>` |
| `transfer` | 主机转移 | `hostInstance` | `POST /api/v1/host/transfer/modules` |

> 批量增删改在网关层被**逐实例展开**为单动作资源，因此 `update` / `delete` 两行策略即覆盖单条与批量场景；
> 上游不存在 `unassociate` 动作，取消关联受 `update` 管控。
>
> 集群/模块/主线实例统一映射为 `biz_topology`，故「创建集群」「创建模块」「编辑」「删除」都归到
> `biz_topology` 的 `create/update/delete`（一行资源类型、多个动作）。主机转移用独立的 `transfer` 动作，
> 与主机本身的 `update` 解耦——「可改主机」≠「可转移主机」。
>
> ⚠️ **`create`（新增实例）现已纳入门禁**：须显式授予 `create` 策略才会放行，未授权返回 `1302102`；
> 其余 `update`/`delete` 维持原门禁逻辑不变。本手册 §五 示例中 `create` 行即为此用意。
> 拓扑写（`biz_topology`）与主机转移（`hostInstance: transfer`）同理须显式授权，未授权返回 `1302102`。
>
> 读类端点（`GET /topo/*`、`POST /topo/statistics`、`POST /topo/hosts/search`、主机转移查询）不匹配网关正则，
> 由 `find` 默认放行规则跳过鉴权，无需也不写入策略。

## 八、收藏类资源隔离（user / OwnerID / BizID）

业务拓扑-主机列表「已收藏条件」与资料目录-模型「标记星」左侧菜单栏收藏，都属于**用户级隔离资源**，
与登录用户相关、按租户（bk_supplier_account）隔离，**不是全局范围**。其隔离维度对齐上游 `FavouriteMeta`：

| 隔离维度 | 字段 | 来源 | 说明 |
|----------|------|------|------|
| 用户 | `bk_user` / `user` | 服务端从登录 token 注入 | 不信任客户端头，杜绝越权归属 |
| 租户 | `bk_supplier_account`（OwnerID） | 服务端从登录 token 注入 | 多租户隔离（默认 `0`） |
| 业务 | `bk_biz_id`（BizID） | 随收藏条件携带 | Host Favorite 专属，按业务隔离 |

### 8.1 Host Favorite（业务拓扑-主机列表「已收藏条件」）

新增 API（与上游 `/api/v3/hosts/favorites` 对齐业务语义）：

- `POST   /api/v1/hosts/favorites`        创建收藏（user/supplier 服务端注入，bk_biz_id 随 body）
- `GET    /api/v1/hosts/favorites`        查询（按 `?bk_biz_id=` 业务过滤，仅返回当前用户 + 本租户 + 本业务）
- `DELETE /api/v1/hosts/favorites/<id>`  删除（WHERE 强制含三层隔离条件，tom 即使拿到 admin 的 id 也无法删除）

底层表 `cc_HostFavourite`（`app/sql/favourite/*.sql`，多方言），数据层 `app/service/favourite_service.py`。
鉴权：上游此资源为 `SkipType`（不进业务 RBAC 判定），故 `app/auth/parser.py` 不覆盖该路由、fail-open 放行，
**隔离完全依赖数据层三层过滤**——与上游「收藏条件无需再单独申请模型权限」语义一致。

**效果**：admin 创建的收藏，tom 既查不到、也删不掉（返回 `1199100`）。

### 8.2 Resource Collection（资料目录-模型「标记星」左侧菜单栏收藏）

走 `user_custom` 表（`app/api/v1/user.py`），按 `user_name` + `bk_supplier_account`（OwnerID，服务端从登录 token 注入）**双层隔离**，对齐上游 `cc_UserCustom` 的 user + supplier 语义；
上游 `cc_UserCustom` 仅含 `bk_user` + `bk_supplier_account` 维度（无 BizID），本裁剪版据此补 OwnerID 维度、不引入业务隔离。
前端 `MENU_RESOURCE_COLLECTION` 收藏即写入该用户的 `user_custom` 配置，彼此不可见。

> 即：两个收藏功能都遵循「与登录用户相关的 per-user 隔离」，tom 无权访问 admin 的收藏数据。
