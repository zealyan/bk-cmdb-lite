# bk-cmdb-lite 权限设计方案（贴近上游 + 无 IAM）

> 目标：参照上游 bk-cmdb v3.10.41 的权限设计（实例新增/删除/修改），为 lite（Flask）设计一套**尽量贴近上游结构**、但**不依赖外部 IAM 服务**的权限框架。
> 适用范围：模型实例 / 主机实例 / 业务（拓扑主线实例）的 create、update、delete、find。

---

## 一、上游权限设计（已读码确认）

### 1.1 架构总览：双层门禁 + 一个总开关

| 层级 | 代码位置 | 行为 |
|---|---|---|
| 总开关 | `src/common/auth/auth.go` → `EnableAuth`（`--enable-auth`，默认 `true`） | `EnableAuthorize()==false` 时**全局短路放行**（返回 `authorized=true`） |
| 网关层 | `src/apiserver/service/filter.go` → `authFilter` | `if !auth.EnableAuthorize() { bypass }`；否则 `parser.ParseAttribute(req)` 把 URL+Method 解析为 `ResourceAttribute[]`，再 `authorizer.AuthorizeBatch` |
| 业务层 | 各 service handler 内 `s.AuthManager.Authorize(kit, ResourceAttribute{...})` | 同上，受 `AuthManager.Enabled()` 控制短路 |

> 结论：**「无 IAM」是上游原生支持的模式**——只要 `enable-auth=false`，apiserver 过滤器与 handler 检查全部短路通过。IAM 只是 `AuthorizeInterface` 的一个实现，鉴权框架与具体鉴权后端完全解耦。

### 1.2 核心抽象（上游 `ac/meta`、`ac` 包）

```go
// src/ac/auth.go —— 鉴权后端接口（可插拔）
type AuthorizeInterface interface {
    AuthorizeBatch(ctx, h, user, resources ...ResourceAttribute) ([]Decision, error)
    AuthorizeAnyBatch(...) ([]Decision, error)
    GetPermissionToApply(ctx, h, resources) (*IamPermission, error)
    RegisterResourceCreatorAction(ctx, h, input) (...)   // 创建者自动授权
    // ...
}

// src/ac/meta/meta.go —— 资源 + 动作
type Action string   // "create" | "update" | "updateMany" | "delete" | "deleteMany" | "find" | ...
type ResourceAttribute struct {
    Basic  Basic          // {Type ResourceType, Action Action, ...}
    // 实例维度还带 InstanceID / SupplierAccount / BusinessID
}
```

实例相关资源类型（`ac/meta/resource.go`）：`business` / `mainlineInstance` / `hostInstance` / `modelInstance` 等。

### 1.3 实例增删改的三条鉴权路径

| 操作 | 上游调用点 | 鉴权构造 |
|---|---|---|
| 新建业务 | `topo_server/service/inst_business.go:52` | `ResourceAttribute{Type: Business, Action: Create}` |
| 新建后自动授权 | `inst_business.go:95` | `Authorizer.RegisterResourceCreatorAction(...)` → **创建者自动获得**该实例的 edit/delete 权 |
| 按业务 ID 鉴权 | `inst_business.go:251` | `AuthorizeByBusinessID(ctx, Update, bizIDs...)` |
| 按实例 ID 鉴权 | `ac/extensions/instance.go:256` `AuthorizeByInstanceID` | 按 `objID` 分发到 host/set/module/app 专属鉴权，否则 `collectInstancesByRawIDs` 后 `AuthorizeByInstances` |

> 关键细节：`AuthorizeByInstances` 内有 `SkipReadAuthorization`（`action==find` 时跳过读鉴权）——上游允许「读不鉴权」，适合本地/开发场景。

### 1.4 多租户隔离

`UserInfo{UserName, SupplierAccount}` 贯穿所有鉴权；资源也带 `SupplierAccount`（bk_supplier_account）。即**权限按供应商账户（id0/id1）隔离**——这与我们之前梳理的 supplier account 租户隔离机制一致。

## 三、lite 权限设计方案（贴近上游、无 IAM）

### 3.1 设计原则

1. **复用上游的同一套「接缝」**：`EnableAuth` 总开关 + `AuthManager.Authorize()` + 可插拔 `Authorizer` 接口。这样未来若接真实 IAM，只需新增一个 `IAMAuthorizer` 实现，业务代码零改动。
2. **默认全放行（对齐上游内置模式）**：lite 默认 `ENABLE_AUTH=False`，与 `enable-auth=false` 等价——当前所有行为完全不变，零回归。
3. **开启后走内置轻量鉴权**：`ENABLE_AUTH=True` 时，用 SQLite 内建一张最小 RBAC 策略，不依赖任何外部服务。
4. **双层门禁对齐**：全局 `before_request`（对应 apiserver `authFilter`）+ handler 内显式 `require_perm(...)`（对应 service 层 `Authorize`）。

### 3.2 模块结构（新增 `app/auth/`）

```
app/auth/
├── __init__.py
├── settings.py        # ENABLE_AUTH 总开关（来自 config，默认 False）
├── resource.py        # ResourceAttribute / ResourceType / Action 常量（对齐 ac/meta）
├── manager.py         # AuthManager：Authorize()、Enabled()、AuthorizeByInstanceIDs()
├── authorizer.py      # Authorizer 接口 + BuiltinAuthorizer（本地 SQLite 策略）
├── parser.py          # 路由+Method → ResourceAttribute[]（轻量版，对应 ac/parser）
└── policy.py          # SQLite 策略存储（supplier / user / resource / action 规则）
```

### 3.3 核心接口（Python 版，对应上游 `ac` 包）

```python
# app/auth/resource.py —— 对齐 ac/meta
class Action:
    CREATE = "create"; UPDATE = "update"; DELETE = "delete"
    FIND = "find"; TRANSFER = "transfer"   # 主机转移（专用动作）
    UPDATE_MANY = "updateMany"; DELETE_MANY = "deleteMany"

class ResourceType:
    MODEL_INSTANCE = "modelInstance"
    HOST_INSTANCE = "hostInstance"
    BUSINESS = "business"
    BIZ_TOPOLOGY = "biz_topology"          # 集群/模块/主线实例（上游 IAM 侧统一为 biz_topology）
    MODEL = "model"

@dataclass
class ResourceAttribute:
    type: str          # ResourceType
    action: str        # Action
    obj_id: str = None # 模型 ID（如 bk_slb）
    instance_id: int = None
    supplier: str = None  # bk_supplier_account（默认 id0）

# app/auth/manager.py —— 对齐 ac/extensions/base.go
class AuthManager:
    def Enabled(self) -> bool:
        return auth_settings.ENABLE_AUTH

    def Authorize(self, user, *resources: ResourceAttribute):
        if not self.Enabled():
            return None, True                 # 短路放行（对应上游 Enabled()==false）
        decisions = self.authorizer.authorize(user, *resources)
        if all(d.authorized for d in decisions):
            return None, True
        return self.authorizer.permission_to_apply(*resources), False

    def AuthorizeByInstanceIDs(self, user, action, obj_id, ids):
        # 对应上游 AuthorizeByInstanceID：按实例 ID 逐条/批量鉴权
        if not self.Enabled():
            return None, True
        return self.Authorize(user, *[ResourceAttribute(obj_id=obj_id,
            instance_id=i, action=action) for i in ids])
```

### 3.4 无 IAM 的两种工作模式

| 模式 | 开关 | 行为 | 对齐上游 |
|---|---|---|---|
| **A. 全放行（默认）** | `ENABLE_AUTH=False` | 任何 `Authorize` 直接返回通过 | `--enable-auth=false` 内置模式 |
| **B. 内置 RBAC（可选开启）** | `ENABLE_AUTH=True` | `BuiltinAuthorizer` 查 SQLite 策略表判定 | 反向工程 IAM 的最小本地实现 |

> 推荐：**默认 A**（与现状一致、无回归）；需要基本保护时开 B。两条路径共用同一套 `Authorize` 接缝。

### 3.5 内置 RBAC 策略模型（模式 B）

```sql
-- app/auth/policy.py 建表（SQLite，复用现有 db）
CREATE TABLE IF NOT EXISTS cc_AuthPolicy (
    id INTEGER PRIMARY KEY,
    supplier   TEXT NOT NULL,          -- 供应商账户（租户隔离）
    principal  TEXT NOT NULL,          -- 用户名（来自 X-User 或配置 admin）
    res_type   TEXT NOT NULL,          -- modelInstance / business / ...
    obj_id     TEXT,                   -- 模型 ID；NULL 表示该类全部
    action     TEXT NOT NULL,          -- create/update/delete/find
    business_id TEXT,                   -- 业务级作用域（biz_topology/hostInstance 专用）；NULL=全部业务（类级）
    effect     TEXT NOT NULL DEFAULT 'allow'
);
```

最小判定规则（对齐上游语义）：
1. **supplier 隔离**：策略必须匹配 `bk_supplier_account`（id0/id1 互不可见）。
2. **创建者自动授权**（对齐 `RegisterResourceCreatorAction`）：实例写入时打 `creator` + `supplier`；该用户对**自己创建**的实例，`update`/`delete` 自动 allow。
3. **管理员全权**：`principal == 配置 ADMIN_USER`（如 `admin`）对所有 supplier 资源 allow。
4. **读可跳过**（对齐 `SkipReadAuthorization`）：`action==find` 默认 allow，降低本地开发噪音。

### 3.6 创建/更新/删除实例的具体鉴权点（映射到现有端点）

| 端点 | 方法 | 动作 | 鉴权调用（插入位置） |
|---|---|---|---|
| `/api/v1/models/<model_id>/instances` | POST | create | `require_perm(user, MODEL_INSTANCE, CREATE, obj_id=model_id)` |
| `/api/v1/models/<model_id>/instances/<instance_id>` | PUT | update | `require_perm(user, MODEL_INSTANCE, UPDATE, obj_id, inst_id)` |
| `/api/v1/models/<model_id>/instances` | PUT | updateMany | 对 body 中每个 `ids[]` 调 `AuthorizeByInstanceIDs(user, UPDATE, model_id, ids)` |
| `/api/v1/models/<model_id>/instances` | DELETE | deleteMany | 对 `ids[]` 调 `AuthorizeByInstanceIDs(user, DELETE, model_id, ids)` |
| `/api/v1/models/<model_id>/instances`（GET/search） | GET | find | 默认放行（SkipReadAuthorization） |

`create_instance` 成功后追加：`stamp creator+supplier` 到实例行 +（模式 B）写一条「创建者自动授权」策略。

### 3.7 全局门禁（对应 apiserver `authFilter`）

在 `app/__init__.py` 的 `create_app` 中加一个 `before_request`：

```python
@app.before_request
def auth_filter():
    if not auth_settings.ENABLE_AUTH:
        return  # 全放行（对齐 authFilter 的 EnableAuthorize 短路）
    attr = parse_route(request)         # parser.py：路由+Method → ResourceAttribute[]
    if not attr:
        return
    resp, ok = auth_manager.Authorize(current_user(), *attr)
    if not ok:
        # 统一返回 HTTP 200 + BaseResp（result:false, bk_error_code=CCNoPermission）
        return no_permission(resp), 200
```

> 注意：lite 路由是干净的 REST，比上游用正则 `ParseAttribute` 简单得多——用「路由表 + Method」即可，无需复杂正则引擎。

### 3.8 用户身份来源（已落地为最小内置鉴权）

身份解析为**四路来源**（详见第六章），优先级：`Bearer` 头 → `bk_token` cookie → `bk_username` / `X-User` 头 → 配置默认用户。其中：

| 来源 | 说明 |
|---|---|
| `Authorization: Bearer <bk_token>` | **主通道**：登录后由前端存 localStorage 并注入（见第六章） |
| Cookie `bk_token` | 对齐上游同名透传形状，服务端同样可解析 |
| Header `X-User` / `bk_username` | 网关注入或开发期自报（dev 回退） |
| 配置 `DEFAULT_USER` | `skipLogin` / 无 token 时的回落（`admin`） |

> 这与上游 `httpheader.GetUser` / `GetSupplierAccount` 的取数方式一致，且天然支撑多租户隔离。第六章的登录接口已取代「前端用户切换器」成为生产身份来源；`X-User` 仅保留为开发期快捷通道。

## 四、实例批量更新的权限预配置过程（结合 RBAC DB 操作）

> 本节约等于「实例批量更新端点的鉴权时序」，把 §3.6 中 `PUT .../instances`（`updateMany`）的鉴权点拆成**逐步 DB 操作**。核心思想（对齐上游 `AuthorizeByInstanceID` → `AuthorizeByInstances` → `batchAuthorize`）：**先只读预校验、再执行写**，任一实例无权则整体/部分拒绝，预校验本身不改任何数据。

> **边界澄清（`ids` 与 `obj_id` 是两个正交维度，切勿混淆）**：
> - **`ids`（实例 ID，`bk_inst_id`）**= 本次要更新的**数据行**标识。它**只**用于 Step ③ 按 ID 取出每条实例的 `creator` / `bk_supplier_account`（owner 信息），供逐实例检查 a/b/c（supplier 隔离、创建者自管）使用。**`ids` 永远不会拿去匹配策略表的 `obj_id`。**
> - **策略表 `cc_AuthPolicy.obj_id`** = **模型级**作用域（如 `bk_slb` 这类模型 ID，或 `NULL` = 该类全部），**不是实例 ID**。Step ④-d 用它与 `:model_id` 比对，得到的是「该用户对该**模型**（全部实例）是否有 update 权」这一个**模型级布尔值**，在请求内只算一次、统一套用到所有 `ids`。
>
> 一句话：**实例级门禁靠 owner（a/b/c），模型级门禁靠策略（d）；两者粒度不同、入参互不替交。** 这是「最小内置 RBAC」的刻意取舍——策略表不做实例级细粒度（上游 IAM 可做到，本方案为简化而把实例级判定下沉到 owner 维度）。

### 4.1 请求形态

`PUT /api/v1/models/<model_id>/instances`（`batch_update_instances`）支持两种 body：

```jsonc
// 形态一：逐条 update 数组
{ "update": [ { "inst_id": 1, "datas": {...} }, { "inst_id": 2, "datas": {...} } ] }

// 形态二：按 ids 批量同值
{ "ids": [1, 2, 3], "data": { "bk_comment": "批量备注" } }
```

两种形态最终都收敛为**一组实例 ID + update 动作**，鉴权逐 ID 进行。

### 4.2 预配置时序（含 RBAC DB 操作）

```
┌─────────────────────────────────────────────────────────────────────────┐
│ PUT /api/v1/models/<model_id>/instances  (batch_update_instances)         │
└───────────────────────────────────┬─────────────────────────────────────┘
                                     │
  ① 解析 body → ids = [1, 2, 3]      │
                                     ▼
  ② ENABLE_AUTH == False？ ──是──▶ 跳过预校验，直接执行 UPDATE（零回归）
                                     │ 否
                                     ▼
  ③ 只读预查 owner（输入=ids，仅此步用 ids）
       SELECT bk_inst_id, creator, bk_supplier_account
       FROM "cc_ObjectBase_0_pub_<model_id>"
       WHERE bk_inst_id IN (:ids)          ← RBAC·DB 只读
                                     │
                                     ▼
  ④ 逐实例 RBAC 判定（循环 rows=③返回的 owner 列表）：             ← 核心
       a. supplier 隔离：inst.supplier == current_user.supplier ?
       b. 管理员全权：  current_user == ADMIN_USER ?
       c. 创建者自管：  inst.creator == current_user ?
       d. 模型级策略（输入=model_id，与 ids 无关）：
          model_allow = SELECT effect FROM cc_AuthPolicy
                        WHERE supplier=? AND principal=?
                          AND res_type='modelInstance'
                          AND (obj_id=? OR obj_id IS NULL)   ← obj_id = model_id，模型级
                          AND action IN ('update','updateMany')   ← RBAC·DB 只读
          命中且 effect='allow' → 该用户对【整个模型】实例有更新权
          （一次请求只算一次，统一套用到所有实例；不看具体实例 ID）
                                     │
                                     ▼
  ⑤ 收集 deny_ids（无权实例）。deny_ids 非空？
       ├─ 是 ─▶ 返回 CCNoPermission + Permissions=[deny 的实例资源]
       │         （对齐上游 GetPermissionToApply），且**不执行任何 UPDATE**
       └─ 否 ─▶ 执行 UPDATE ... WHERE bk_inst_id IN (:ids)
```

### 4.3 具体 RBAC DB 操作（SQLite 语句）

**Step ③ 取实例 owner（只读，不改数据）**

```sql
-- 复用 InstanceService.get_instances_by_ids(model_id, ids)
SELECT bk_inst_id, creator, bk_supplier_account
FROM "cc_ObjectBase_0_pub_<model_id>"
WHERE bk_inst_id IN (1, 2, 3);
-- 返回：[{bk_inst_id:1, creator:'alice', bk_supplier_account:'0'},
--        {bk_inst_id:2, creator:'bob',   bk_supplier_account:'0'},
--        {bk_inst_id:3, creator:'alice', bk_supplier_account:'0'}]
```

> 说明：自定义模型表名规则为 `cc_ObjectBase_0_pub_{model_id}`（`instance_service._get_table_name`）；内置模型走 `cc_ApplicationBase / cc_SetBase / cc_ModuleBase / cc_HostBase`，在同位置取表名。实例行已含 `creator`、`bk_supplier_account` 列（migrate 定义），可直接用于判定。

**Step ④-d 查策略表（只读）**

```sql
SELECT effect FROM cc_AuthPolicy
WHERE supplier      = :supplier          -- 当前用户供应商账户（如 '0'）
  AND principal     = :user              -- 当前用户名（来自 X-User，默认 admin）
  AND res_type      = 'modelInstance'
  AND (obj_id       = :model_id OR obj_id IS NULL)   -- 命中具体模型 或 该类全部
  AND action        IN ('update', 'updateMany');
-- 命中且 effect='allow' → 该用户对该模型实例有更新权（无视具体实例 owner）
```

**Step ④ 逐实例判定逻辑（伪代码，对齐上游 AuthorizeByInstances）**

```python
def pre_authorize_update(user, supplier, model_id, ids) -> (allowed_ids, deny_ids):
    rows = get_instances_by_ids(model_id, ids)          # Step ③ SQL：用 ids 取 owner
    # ── 模型级策略：用 model_id 查一次，与 ids 无关（见 Step ④-d）──
    model_allow = query_policy_allow(supplier, user,    # Step ④-d SQL
                                     'modelInstance', model_id, 'update')
    deny_ids = []
    for inst in rows:                                   # rows 来自 ③，不是 ids 本身
        if inst['bk_supplier_account'] != supplier:     # a. supplier 隔离（用 owner）
            deny_ids.append(inst['bk_inst_id']); continue
        if user == ADMIN_USER:                          # b. 管理员全权
            continue
        if inst['creator'] == user:                    # c. 创建者自管（用 owner；对齐 RegisterResourceCreatorAction）
            continue
        if model_allow:                                 # d. 模型级策略授权（不看具体实例 ID）
            continue
        deny_ids.append(inst['bk_inst_id'])            # 以上皆否 → 无权
    allowed_ids = [i for i in ids if i not in deny_ids]
    return allowed_ids, deny_ids
```

### 4.4 拒绝响应（对齐上游 GetPermissionToApply）

上游 `AuthorizeBatch` 返回 `authorized=false` 时调用 `GetPermissionToApply` 拼出 `Permissions`（含被拒资源类型/实例 ID），响应体为 `CCNoPermission`。lite 对应：

```python
if deny_ids:
    permission = {
        "permissions": [{
            "type": "modelInstance",
            "action": "update",
            "obj_id": model_id,        # 模型级作用域（=model_id，与实例 ID 无关）
            "instance_ids": deny_ids,  # 被拒的【数据行】实例 ID（与上面的 obj_id 正交）
            "supplier": supplier,
        }],
    }
    # 统一返回 HTTP 200 + BaseResp（result:false, bk_error_code=CCNoPermission）
    return no_permission(permission), 200
# 否则才执行写
execute(f'UPDATE "cc_ObjectBase_0_pub_{model_id}" SET ... WHERE bk_inst_id IN ({allowed_ids})')
```

### 4.5 预配置前置：创建时打标（让 ④-c 生效）

当前 `create_instance` 仅默认 `bk_supplier_account='0'`，未写入 `creator`。要让「创建者自管」在批量更新时真正生效，需在**创建端点**落标：

```python
# model.py create_instance 端点：把当前用户写入 creator
instance_data['creator'] = current_user()          # 来自 X-User，缺省 admin
instance_data['bk_supplier_account'] = current_supplier()  # 来自 X-Supplier-Account，缺省 '0'
result = InstanceService.create_instance(model_id, instance_data)
# 创建者自管仅依赖上面这行 creator 打标（实例级），不再写 cc_AuthPolicy 策略行。
# ⚠️ 历史实现曾在此写【模型级】allow(update/delete)，已于「§九 上游对齐」移除：
#    cc_AuthPolicy 无 instance_id 列，写模型级 allow 会造成权限放大——
#    创建 1 个实例即获得该模型【全部实例】的 update/delete 权。
# 对齐上游 RegisterResourceCreatorAction（创建者仅对【该实例】获得 edit/delete/view）。
```

> 注意：`creator` 须纳入实例表的**可写字段白名单**（当前 `valid_fields = 模型属性 ∪ SYSTEM_FIELDS`），否则会被 `clean_data` 过滤丢弃。`SYSTEM_FIELDS` 中应加入 `'creator'`（与 `bk_supplier_account` / `create_time` / `last_time` 同列）。

### 5.2 如何开启「模式 B」（内置 RBAC）

默认 `ENABLE_AUTH=False`：全局短路放行，行为与现状完全一致（零回归）。开启步骤：

```bash
# 后端启动时设置环境变量（与 SKIP_LOGIN 正交）
export CMDB_ENABLE_AUTH=true        # 开启内置 RBAC
export CMDB_SKIP_LOGIN=false         # 关闭跳过登录，强制 token 身份（否则未认证请求会被拒绝）
# 然后重启后端（supervisord: python3 /tmp/spctl.py restart preview-5000）
```

- `ENABLE_AUTH=True` + `SKIP_LOGIN=true`：仍按 `DEFAULT_USER=admin` 回落为超管全权（dev/演示场景，便于不开登录页也能验 RBAC）。
- `ENABLE_AUTH=True` + `SKIP_LOGIN=false`：必须持有效 `bk_token`；无 token 且非 `admin` 的写操作返回 `1302102`（CCNoPermission），未认证返回 `1302100`。
- 鉴权语义：① supplier 隔离（id0/id1 互不可见）→ ② 管理员全权（`bk_role==1`）→ ③ 创建者自管（实例 `creator` 命中）→ ④ 模型级策略（`cc_AuthPolicy` 命中，含批量动作）→ 否则拒绝。读操作（`find`）始终放行（对齐 `SkipReadAuthorization`）。

### 5.3 端到端验证结论

独立临时库 + `ENABLE_AUTH=true` + `SKIP_LOGIN=false` 跑通 **15/15** 用例（已清理源库，不污染线上 `cmdb_dev.db`）：

| 用例 | 期望 | 结果 |
|---|---|---|
| admin 登录 / 创建实例打 `creator=admin` | 成功 | ✅ |
| admin 更新/删除/批量自身实例 | 放行（管理员全权） | ✅ |
| 普通用户无策略 → 更新/删除/批量 | 拒绝 `1302102` | ✅ |
| 普通用户持模型级策略 → 更新/删除/批量 | 放行 | ✅ |
| 跨 supplier（`id1`）更新 `id0` 实例 | 拒绝（supplier 隔离） | ✅ |
| 未认证写操作 | 拒绝 `1302102` | ✅ |
| 读列表 | 放行（find 跳过鉴权） | ✅ |

### 5.4 几处实现取舍（与原设计略有差异，已确认合理）

1. **创建（create）已纳入门禁（对齐上游，行为变更）**：早期版本为「创建在粗粒度层放开」——`auth_filter` 对 `create` 资源直接 `return`、不要求 `create` 策略。该做法实则将上游「创建者自管」与「创建动作门禁」两件事混为一谈：上游 `genDynamicAction` 为每个模型注册独立的 `Create_<模型>` 动作，创建**前**即须过 `Create` 权限校验（而 `RegisterResourceCreatorAction` 仅授创建者 `edit/delete/find`，**不含 create**）。现移除 `auth_filter` 中那段 `create` 提前 `return`，`create` 与 `update`/`delete` 走同一套 `coarse_authorize` → `query_allow` 判定；未授权即 `1302102`。至此「不可新增」可由「不授 `create` 策略」实现，与上游一致。
2. **批量动作同权匹配**：`BuiltinAuthorizer` 将 `updateMany/deleteMany` 同时匹配 `update/delete` 策略（见 §4.4 `action IN ('update','updateMany')`），`grant_creator` 亦一并授予批量动作，避免批量端点被粗粒度层误拒。
3. **handler 用实例级 `check_instances` 而非仅模型级 `require_perm`**：单实例 update/delete、批量 update 均走 §4 的逐实例 owner 判定（a/b/c/d），比 §3.6 描述的模型级 `require_perm` 更细，能精确回报被拒的 `instance_ids`（对齐 `GetPermissionToApply`）。
4. **`creator` 列落地方式**：新模型实例表在 `migrate.create_instance_table` 即含 `creator`；历史/已存在实例表由启动时 `ensure_creator_columns()` 用 `ALTER TABLE ADD COLUMN` 补齐；`SYSTEM_FIELDS` 加入 `creator` 使其可写。

## 六、最小内置鉴权方案（已实现）

> 目标：在不引入登录组件服务 / 外部 IAM 的前提下，提供**登录接口 + 独立登录页 + token 有效期**，并与上游 `bk_token` 数据形状贴合。代码已落地于 `app/auth/`（后端）与 `src/views/login`、`src/auth.js`（前端）。**不实现**导航栏用户 selector 切换器（按需求去掉）。

### 6.1 与上游数据形状对齐

| 上游概念 | 上游形状 | lite 实现 |
|---|---|---|
| 会话令牌 | `bk_token` cookie（签名令牌，携带用户名+供应商） | `itsdangerous.TimedSerializer` 签名 token，cookie / `Authorization: Bearer` 双通道，名称仍为 `bk_token` |
| 身份头 | `bk_username` / `bk_supplier_account` | `current_user()` 同样认这两条头（网关注入 / dev 自报） |

| 登录接口 | `POST /auth/login` → `{ bk_token, username }` | `POST /api/v1/auth/login`，响应形状同 |

> 不引入 JWT：`itsdangerous` 已随 Flask 安装，语义等价（签名 + 携带身份 + 可过期），零新增依赖。`max_age` 校验在 `loads` 阶段（TimedSerializer 自带时间戳），`dumps` 不传时限参数。

### 6.3 接口与数据形状

- `POST /api/v1/auth/login`：`{bk_user_name, bk_password}` → `{bk_token, bk_user_name, bk_role}`；账密错返回 `bk_error_code=1302101`。
- `GET  /api/v1/auth/me`：
  - `SKIP_LOGIN=true` → `{bk_user_name:'admin', skipLogin:true}`（前端据此直接进主页）；
  - 携带有效 `bk_token` → 返回该用户信息 + `skipLogin:false`；
  - 无有效 token 且 `SKIP_LOGIN=false` → `result:false, bk_error_code=1302100`（前端据此跳登录页）。
- `POST /api/v1/auth/logout`：无状态 token，服务端无需销毁，前端清 localStorage/cookie 即失效。
- 用户表 `cc_UserBase`：`bk_user_name`(UNIQUE) / `bk_supplier_account` / `bk_role`(1=超管) / `bk_password`(werkzeug 哈希) / `create_time`。应用启动时 `init_user_table()` + `bootstrap_admin()` 保证表与初始超管存在。

### 6.4 前端实现（localStorage + token 双轨）

| 文件 | 职责 |
|---|---|
| `src/auth.js` | `getToken/setToken/clearToken` + `ensureAuth()`（首导航调 `/me` 判定登录态并缓存）；token 存 localStorage，同时写 `bk_token` cookie 对齐上游 |
| `src/api/auth.js` | `login / me / logout` 封装 |
| `src/views/login/index.vue` | **独立登录页**（全屏卡片，用户名/密码表单，提交后 `setToken` 并回跳 `redirect` 地址） |

> **skipLogin 开关行为**：`SKIP_LOGIN=true`（默认）→ `/me` 返回 `skipLogin:true`，前端守卫直接放行、不显示登录页；`SKIP_LOGIN=false`（部署时设 `CMDB_SKIP_LOGIN=false`）→ 未带有效 token 的请求被守卫拦截跳登录页，登录后凭 `bk_token` 进入。

### 6.5 与 RBAC（§3.5/§4）的衔接

- `current_user()` 取自 token 的 `bk_user_name`，直接喂给 §4 批量更新预校验的「创建者自管」「管理员全权（读 `bk_role==1`）」「supplier 隔离」。
- `require_login()` 装饰器在 `SKIP_LOGIN=false` 时拦截无 token 请求返回 `1302100`；`ENABLE_AUTH`（RBAC 判定）为**另一独立开关**，两者正交——登录负责"你是谁"，RBAC 负责"你能干什么"。当前仅前端守卫强制登录，后端逐端点 401 强制留待 `ENABLE_AUTH` 一轮落地。

1. **先加总开关与空实现**：新增 `app/auth/`，`ENABLE_AUTH=False` 默认短路。此时行为=现状，可立即提交。

## 九、上游对齐改造（模型实例动作模型 / 关联鉴权 / 创建者授权）

> 背景：现象是「`bk_slb_listener` 无法删除与取消关联，而权限本应只收紧在 `bk_switch`」。
> 排查发现三处偏离上游，本章记录对齐结果。依据均来自上游源码，非推测。

### 9.1 上游的模型实例权限模型（事实依据）

| 维度 | 上游实现 | 源码位置 |
|---|---|---|
| 授权语义 | **纯 allow 白名单，无 deny 概念** | `src/ac/iam/*`（全局无 deny 标识） |
| 实例动作 | **仅 4 个**：`create`→Create、`update`→**Edit**、`delete`→Delete、`find`→View；其余（含 `updateMany`/`deleteMany`）返回 `Unsupported` | `ac/iam/adaptor.go:207` `ConvertSysInstanceActionID` |
| 动作注册 | 每个模型动态生成 `{view,create,edit,delete}_sysinstance{modelID}` | `ac/iam/adaptor.go:724-762` |
| 批量端点 | parser 层取 `delete.inst_ids` **逐实例展开**为多个单动作资源，不存在 obj 级批量动作 | `ac/parser/topolatest.go:1185-1194` |
| 取消关联 | 按 `association_id` **查关联记录**，对 `bk_obj_id` 与 `bk_asst_obj_id` **双方模型**各生成一个 **update(Edit)** 资源；自关联时对两个实例各生成一个 | `ac/parser/topolatest.go:735-799` |
| 创建者授权 | `RegisterResourceCreatorAction` 为**实例级**，授予 Edit/Delete/Find，**不含 Create** | `ac/iam/initial_resource_creator_actions.go:20` |
| 读跳过 | `SkipReadAuthorization && (Find||FindMany)` → 放行 | `ac/extensions/instance.go:295` |

> 关键推论：**上游没有独立的「取消关联」权限**——它由 `update(Edit)` 管控。
> 因此「某用户不能取消 X 的关联」在上游的唯一表达是「不授予其 X 的 `update` 权」。

### 9.2 三处偏离与修复

| # | 偏离 | 后果 | 修复 |
|---|---|---|---|
| 1 | 自造 `unassociate` 动作；批量端点产出 `deleteMany`/`updateMany` obj 级资源 | 动作集与上游不一致，白名单策略需按 lite 私有动作配置 | `parser.py` 归一到 4 基础动作；批量端点逐实例展开。`resource.py` 移除 `UNASSOCIATE`，`many` 常量降级为历史数据兼容 |
| 2 | 取消关联只用 URL 携带的 `obj_id` **单侧**鉴权 | **权限绕过**：同一条关联换对端入口即可删除，且双向删除会连带清掉受保护模型侧的记录 | `parser._parse_unassociate`：查关联记录 → 双方模型各一个 `update` 资源，任一侧无权即整体拒绝 |
| 3 | `grant_creator` 写**模型级** allow（表无 `instance_id` 列） | **权限放大**：创建 1 个实例 → 获得该模型全部实例的 update/delete 权，可绕过针对该模型的收紧 | `on_instance_created` 不再写策略行；创建者自管改由 `creator` 列承担，并在 `coarse_authorize` 下沉实例级判定 |

### 9.3 网关层判定下沉（配合修复 3）

`parser` 逐实例展开后资源普遍带 `instance_id`，`coarse_authorize` 相应分两路：

- **带 `instance_id`**：按 `(obj_id, action)` 归并后走 `check_instances`
  （supplier 隔离 → 创建者自管 → 模型级策略），使「创建者自管」在网关层即生效；
- **不带 `instance_id`**：退化为模型级策略判定。

任一资源无权 → 整体拒绝（对齐上游 `GetPermissionToApply`）。

### 9.4 策略配置范式（以 tom 为例）

上游无 deny，故「收紧某模型」= **不授予**该模型对应动作，而非写 deny：

| 模型 | create | update | delete | find | 效果 |
|---|:--:|:--:|:--:|:--:|---|
| `bk_slb` / `bk_slb_listener` / `bk_slb_server` | ✅ | ✅ | ✅ | ✅ | 可增删改查、可取消关联 |
| `bk_switch` | ✅ | ❌ | ❌ | ✅ | 可建可查；**不可改、不可删、不可取消关联** |

> ⚠️ 取舍说明：因取消关联受 `update` 管控，要达成「不可取消关联」**必须**同时不授予 `update`，
> 即「不可编辑」是上游模型下的**必然连带**，无法在不偏离上游的前提下拆分。
>
> ⚠️ 创建者自管仍生效：tom 自建的 `bk_switch` 实例（`creator='tom'`）仍可由其删除，
> 这是上游 `RegisterResourceCreatorAction` 的既定语义；但已**不再放大**到他人实例。

> ⚠️ **create 已纳入门禁（行为变更）**：上表「create」列现在真实生效——只有显式授予 `create`
> 策略才允许新建实例，未授予则创建被 `1302102` 拒绝。早期版本 `create` 对全体已登录用户开放、
> 不受策略约束，现已移除该豁免、对齐上游。`bk_switch` 行的「✅ 可建」表示已显式授 `create`。

## 十、业务拓扑权限（biz / set / module / transfer）

> 背景：业务拓扑页（`#/business/<id>/index`）的写操作（创建集群、编辑/删除集群、创建/编辑/删除模块、主机转移）此前**未纳入门禁**——网关层只分类了模型实例动作，拓扑路由一律 `return None` 放行。本章把这套动作对齐上游，纳入 `coarse_authorize` 的模型级策略判定。

### 10.1 上游设计（已读码确认）

| 维度 | 上游实现 | 源码位置 |
|---|---|---|
| 资源类型（集群/模块/主线） | IAM 侧统一为 `biz_topology`（CMDB 内部 `modelSet`/`modelModule`/`mainlineInstance` 三者在 `ccIamResTypeMap` 全映射成 `BizTopology`） | `src/ac/iam/adaptor.go:57-116` |
| 资源类型（业务） | IAM 侧为 `biz`（非 `business`）；业务**无 delete 动作**，归档用 `archive_business` | `src/ac/iam/types.go:247` |
| 资源类型（主机） | IAM 侧为 `host`；转移是专用动作 `edit_biz_host` / `host_transfer_across_business` / `assign_host_to_biz` / `unassign_biz_host` | `src/ac/iam/types.go:331-396` |
| 动作命名 | 编辑一律 `edit_*`（CMDB 内部 `meta.Update` 映射为 IAM 的 `edit_*`）；**不存在 `update_*` IAM 动作** | `src/ac/iam/adaptor.go:228-349` `resourceActionMap` |
| 动作映射 | `modelSet/modelModule/mainlineInstance`：create→`create_biz_topology`、update→`edit_biz_topology`、delete→`delete_biz_topology`、find→Skip | `adaptor.go:323-343` |
| 业务创建 | `ResourceAttribute{Type: Business, Action: Create}`（handler 内显式授权） | `src/scene_server/topo_server/service/inst_business.go:52` |
| 主机转移 | 跨业务：`MoveHostToAnotherBizModule` → `host_transfer_across_business`（源+目标双业务 Layer 单层组合，任一侧无权即拒）；业务→池：`unassign_biz_host`；池→业务：`assign_host_to_biz` | `src/ac/parser/host.go:946`、`adaptor.go:284-295` |

> 关键结论：**集群/模块/主线实例在上游是同一类资源 `biz_topology`**，create/edit/delete 三个动作即覆盖全部拓扑写操作；业务删除用 archive（lite 未暴露业务删除路由，故暂不门禁）。**主机转移是独立动作**，与主机本身 `edit` 正交——lite 用 `transfer` 动作区分，避免「可改主机属性」与「可转移主机」被同一策略耦合。

### 10.2 lite 资源类型与动作

| lite `ResourceType` | 值 | 覆盖上游资源 | 动作（lite `Action`） |
|---|---|---|---|
| `BIZ_TOPOLOGY` | `biz_topology` | 集群 / 模块 / 主线实例（= 上游 `biz_topology`） | `create` / `update` / `delete` |
| `HOST_INSTANCE` | `hostInstance` | 主机（转移用） | `transfer` |

- 复用 §3.5 的同一张 `cc_AuthPolicy` 表与 §4 的判定链（`coarse_authorize` → `query_allow`）。**对齐上游 `bizTopology` 的 `Parents=[business]`，本表新增 `business_id VARCHAR(64)` 列**承载「业务级作用域」维度（详见 §10.4）。
- 拓扑写操作**不带 `instance_id`**（模型级作用域），与上游 `biz_topology` 的模型级策略语义一致；因此走 `coarse_authorize` 的 `model_level` 分支（不触发实例级 owner 判定）。**业务级隔离额外由 `business_id` 维度承载**：解析器（`app/auth/parser.py`）从路由反推 `business_id`——创建集群取自 `<bizId>`；创建模块 / 编辑 / 删除节点由 `set`/`module` 的 `instId` 反查 `cc_SetBase`/`cc_ModuleBase` 的 `bk_biz_id`——写入 `ResourceAttribute.business_id`，判定时与策略 `business_id` 列比对。

### 10.3 路由 → 动作映射表（parser.py）

| 端点 | 方法 | lite 资源 / 动作 | 上游对应 | 拦截？ |
|---|---|---|---|---|
| `/api/v1/topo/biz/<bizId>/set` | POST | `biz_topology` / `create` | `create_biz_topology` | ✅ 门禁 |
| `/api/v1/topo/set/<setId>/module` | POST | `biz_topology` / `create` | `create_biz_topology` | ✅ 门禁 |
| `/api/v1/topo/node/<objId>/<instId>` | PUT | `biz_topology` / `update` | `edit_biz_topology` | ✅ 门禁 |
| `/api/v1/topo/node/<objId>/<instId>` | DELETE | `biz_topology` / `delete` | `delete_biz_topology` | ✅ 门禁 |
| `/api/v1/host/transfer/modules` | POST | `hostInstance` / `transfer` | `edit_biz_host` / `host_transfer_*` | ✅ 门禁 |
| `/api/v1/topo/biz`（及 `/biz/<id>/set`、`/set/<id>/module` 等 GET） | GET | `None` → 放行 | find 跳过鉴权 | ❌ 放行 |
| `/api/v1/topo/statistics`、`/api/v1/topo/hosts/search` | POST | `None` → 放行（读类） | find 跳过鉴权 | ❌ 放行 |
| `/api/v1/host/transfer/topology|internal|host/modules` | GET/POST | `None` → 放行（读类） | find 跳过鉴权 | ❌ 放行 |

> `<objId>` ∈ `{set, module}`（及任意主线 obj）——lite 不区分 set/module 资源类型，统一映射为 `biz_topology`（与上游 IAM 侧一致）。

### 10.4 策略配置范式（CLI）

拓扑策略复用 `cmdb auth policy grant`，新增 `--res-type` 指定资源类型（`--model` 仍填 obj_id 作用域）：

```bash
# 授予用户对「全部业务」集群/模块 的 创建/编辑/删除 权（省略 --biz-id = 类级，覆盖全部业务）
python3.11 -m app.cli.cmdb auth policy grant \
  --user <用户名> --res-type biz_topology --model biz_topology \
  --action create,update,delete

# 仅授予用户对「业务 2」集群/模块 的 创建/编辑/删除 权（--biz-id 2 = 业务级，仅业务 2 生效）
python3.11 -m app.cli.cmdb auth policy grant \
  --user <用户名> --res-type biz_topology --model biz_topology \
  --action create,update,delete --biz-id 2

# 授予用户「主机转移」权（与主机 edit 独立；同样可加 --biz-id 限定业务）
python3.11 -m app.cli.cmdb auth policy grant \
  --user <用户名> --res-type hostInstance --model host --action transfer

# 仅授予用户对「业务 2」的主机转移权（--biz-id 2 = 业务级，仅业务 2 的模块可转移主机）
python3.11 -m app.cli.cmdb auth policy grant \
  --user <用户名> --res-type hostInstance --model host --action transfer --biz-id 2

# 撤销「全部业务」拓扑策略 / 仅撤销「业务 2」拓扑策略 / 列出
python3.11 -m app.cli.cmdb auth policy revoke --user <用户名> --res-type biz_topology --model biz_topology --action create
python3.11 -m app.cli.cmdb auth policy revoke --user <用户名> --res-type biz_topology --model biz_topology --action create,update,delete --biz-id 2
python3.11 -m app.cli.cmdb auth policy list   --user <用户名> --res-type biz_topology
```

> **业务级作用域（`business_id`）已落地**：`cc_AuthPolicy` 新增 `business_id VARCHAR(64)` 列（可为 `NULL`），承载「按业务隔离」维度，对齐上游 `bizTopology` 的 `Parents=[business]`（集群/模块）与 `host transfer` 的 `Parents=[business]`（主机转移）。授权时通过 CLI `--biz-id` 指定：
> - **省略 `--biz-id`**（默认）→ `business_id=NULL` **类级策略**，覆盖**全部业务**（即旧的「业务无关」行为默认保留，单条策略对所有业务生效）。
> - **`--biz-id 2`** → `business_id='2'` **业务级策略**，仅对业务 2 生效；与类级策略是**两条互相独立**的行（互不覆盖、互不幂等跳过）。适用于 `biz_topology`（集群/模块）与 `hostInstance`（主机转移）两类资源。
>
> **请求时业务作用域如何确定（parser 反推）**：
> - `biz_topology`：由 URL `/topo/biz/<bizId>/set` 或目标 `set`/`module` 的 `instId` 反查 `cc_SetBase`/`cc_ModuleBase.bk_biz_id`。
> - `hostInstance`（`transfer`）：由请求体 `module_id` 反查 `cc_ModuleBase.bk_biz_id`——即「把主机转移到**哪个业务的模块**」决定本次操作的业务作用域（对齐上游 `host_transfer` 的 `Parents=[business]`）；请求体 `bk_biz_id` 作为退化来源，再不行则 `NULL`（仅类级策略可放行）。故「仅授 `--biz-id 2` 转移权」的用户，转移到业务 2 模块放行、转移到业务 1 模块被拒。
>
> 判定规则（`policy_query_allow`）：请求解析出的 `business_id` 命中 `business_id=<本业务>` **或** `business_id IS NULL`（类级）即放行。因此「类级策略」是全部业务的**超集**。per-biz × 类级的隔离已通过端到端验证（`e2e_biz_auth.py` 25/25 + `e2e_host_transfer_auth.py` 13/13，2026-08-13）。详见 `CLI使用手册-权限设置篇.md` §4.4–§4.7 与 §7.3。
>
> ⚠️ 业务本身的「查询」走 `/api/v1/topo/biz`（GET，读，放行）；业务「创建/编辑/删除」在 lite 未暴露独立 topo 写路由（若经由模型实例 `bk_biz` 的 create，则已被 §九 的模型实例机制覆盖）。故本章门禁范围限定为集群/模块/主机转移。
